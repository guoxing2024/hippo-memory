## [0.3.2] — 2026-09-25（批次日期）／ **2026-10-06 发布 npm**（同日 **0.3.3** 仅重发本包文档，代码成员与 0.3.2 逐字节相同）— `memory_verify` 的返回值补上两种"不是 yes"（需要引擎 `hippo-memory-core@^0.3.2`）

与 DSH 适配层同构的一版：把引擎侧 `verify` 的契约订正透传给模型。**yes 现在需要锚**，`OUT_OF_SCOPE` 现在会点名否决它的那条前提；缺陷本体、根因与修都在引擎，见根 [CHANGELOG.md](../../CHANGELOG.md) 的 `[0.3.2]`。

### Changed — `memory_verify` 工具面

- **返回新增 `weak_match` / `scope_conflicts`**（缺字段分别规范为 `false` / `[]`）：前者=有痕迹越过召回线但没有任何东西把它锚到这句话上（只是同话题）；后者=与调用方 `scope` 前提冲突、匹配度不低于所选支持的那些痕迹，它们的存在使裁决成为 `OUT_OF_SCOPE`。
- **description 点名五种结局**：SUBSTANTIATED / CONTRADICTED / OUT_OF_SCOPE / WEAK_MATCH / UNSUBSTANTIATED，并写明只有 `substantiated: true` 是证据。
- **`DISCIPLINE` 的 VERIFY 一条补两句**：`scope_conflicts` 里就是与你的前提互斥的那几行；`weak_match:true` 与"查不到"是同一种回答——**去真实来源复查的线索，不是可以据以断言的证据**。

### Fixed — F5（黑盒报告 #6，本包自家缺陷）：没声明的参数被丢掉，而调用方收到成功

- **症状**：本包宿主把模型写出的 JSON **原样**交给工具，`@deepseek-ai/dsh-tools` 的参数对象 schema 又不带 `additionalProperties`（隐式开放参数对象），于是 `memory_remember({ ..., detail2: 'typo', not_a_field: true })` 这一形**返回成功**——多余键被引擎直接扔掉、哪一列都不携带它，而工具卡片回显的 `rawInput` 里它们还在，看起来像写进去了。写的人以为写进去了。（与 DSH 那一条同源：0.3.2 那份文件从第 270 行起的注释与 DSH 的 `defineClosedTool` 读的是同一件事，两条缺陷分别落在两个边界上。）
- **根因**：`buildTools` 里的 `define` 只按 `definition.args` **取已知键**（0.3.2 那份文件的第 277 行），从不检查**多余的**键。边界是唯一知道自己声明了什么的地方，所以这句话只能在这儿说。
- **修法**：未声明的参数名一律**拒**（0.3.2 那份文件的第 283 行），回显 `unknown argument(s) … — not declared, so nothing was read or written. Declared: …`，让一次拼写错误在第一次调用后就终止；被拒的写入**不落盘**（用例断言 recall 之后 `hits.length === 0`）。
- **未收（写在这里而不是藏在根目录）**：① 这道守卫在 `definition.args` 为空时**直接透传**（0.3.2 那份文件的第 279 行）——那是给"宿主换了形状、声明表取不到"留的退路，但它同时意味着一个**不声明任何参数的工具**不受这条保护；② 直接用引擎 API 的调用方不受约束；③ 参数的**值类型**照旧不校验，这一轮只管名字。三条都在 [ROADMAP](../../ROADMAP.md) 在册。

### Changed — `memory_recall` 的返回补上 `anchored` / `anchors`（引擎 F4b 的透传）

- 每条命中多两个字段：`anchored`（这一行与 cue 之间有没有可指认的依据）与 `anchors`（依据是哪一档：`identifier` / `entity` / `subject` / `vocabulary` / `recency`）。**这一条对本包不是可有可无的装饰**：`hitView` 是**逐字段列出**的白名单，引擎那边多出来的字段若不在这里点名就永远到不了模型——所以 F4b 在引擎侧修的是判据，在本包这边修的是出口。`DISCIPLINE` 里"命中不等于证据"那句从此有可读字段可依。
- **含义要说清**：`relativeScore` 是"除以本组最高相似度"，组里最好那条**永远是 1.000**，它表达排序不表达置信度；`anchored: false` 说的正是"这一行只靠向量距离坐在这个位置"。
- 缺陷本体、根因与 belt 的代价（四臂面板：bge 下 facts-only 2/24、strict 5/24，哈希空间 0/17——那类形状在兜底空间结构上不存在）都在引擎，见根 [CHANGELOG.md](../../CHANGELOG.md) 的 F4b 一节。本包另有两处随引擎语义一起变、**无代码改动**：`scope` 现在认裸词（两条不同的裸前提互相否决而不是互相代答，见根 F1），`newer_related` / `contradicting` / `stale_support` 现在按被问的前提筛（见根 F2）；`duplicates` / `merge` 的向量通道与 `consolidated` 一词一义同样只动引擎。

是第五轮普查挖出的、比 R4 族低一层的一条：五枚锚里**没有一枚读值位**——库里 `gto deploys to staging cluster`、问 `… production …` 盖章 yes，而把 `production` 换成一个**根本不存在的词** `zzzqqq` 照样盖章（报告者自己做的控制实验，本机两空间复跑确认）。修法是一条**位置**判据 `wordFlip`，作为**第三枚 belt** 接在极性与标识符两枚旁边，落 `WEAK_MATCH` 而**不给** `CONTRADICTED`（一个谓词可以对多个值同时为真）。**这一枚对本包特别有用**：它不要求行里带实体、不要求带工单号 / sha、也不要求句式落在系动词表内——只要求"两句话只差一个词，而那个位置两侧都像值"，而这正是本包那种无结构散文行的常见形状。**V2（第六轮复测）换掉的正是这一枚的前提**：它原先还要求"分歧之前有 ≥4 个实字符"，量的却是分歧离句首多远，于是同一个数两侧各错一次——`the primary handles writes` 对 `… standby …` 盖章 yes（bge 0.831），语义相同、前面多一个真词的那对反而在更高的 0.876 上被否掉，**没有阈值能同时修两侧**。判据改成**哪一位动了**：剥掉连接词与冠词后分歧前什么都不剩，动的是主语（同样只降级，note 也不再谎称存在共同主体）；两侧在分歧处陈述**同一个数**则不降级（`… configured 30 seconds` 对 `… capped 30 seconds` 回到 yes，中文 `设定为 30 秒` 对 `最多 30 秒` 在 bge 下也回到 yes，0.94），**换数字仍判反证**。对本包的含义：宿主写下的无结构散文行里，"主语换了"与"措辞换了但数值没换"这两种从此各有正确的读数，而 belt 依旧只降级、从不收紧。**它也有一个已量的边界**：不带空格的中文（`超时30秒`）在它之外（连召回线都过不了）。第四条是四处出口把四舍五入后的分数写进不等式（`best similarity 0.54 < 0.54` 这类自己不成立的句子）。本包**无代码改动**，几条都以 `note` 文案原样透传。**R7a** 同数豁免跨连接词不再放行，**R7b** 值词拉丁下限 4→3（`aws→gcp` 照旧 `WEAK_MATCH`，对本包这类无结构散文行即"短值翻转不再盖章"）。**R9** `valueClash` 加屈折词形还原（`run`→`runs`、`lane`→`lanes` 这类单复数不再是两个值，对本包散文行即"复数改写不再落 CONTRADICTED"；只碰 `s` 屈折，`ed` 与缩写不动）。**R10** 去尾 `s` 把 `https`/`http` `premise-narrowing:`。对本包用户可观测的三件事：① **写入侧**——同一句话存两遍、第二遍带 `scope`，过去返回 `outcome:"none"` 且库里那一行的前提被原地补上（不升版本、不进 `history`，通说就此消失），现在两条并存；确实要窄化得显式 `supersedes: [id]` 或 `update()`。② **读取侧**——一条不写前提的行**逐字**复述主张时，即使调用方给的前提与旁边那条带前提的孪生行冲突仍答 `substantiated`；这是对 D2 那条否决规则**开的一个只限同一句话的口子**，因为并存裁决本身造出"通说 + 带前提孪生"这个形状，换措辞问照旧 `out_of_scope`（面板 R11 实测，两空间相同）。③ **清理侧**——`memory_maintain` 的 `duplicates` 会把这一对讲成一组并标 `mixedPremises: true`，`merge` 两个方向都拒绝折叠、把被拒的行放进 `blocked[]`；**本包这条透传是按字段清洗的**——`blocked[].reason` 过 `clean()`（引擎的理由文本带着记忆原文），新写的两句方向理由 `states a premise where the survivor states none (…)` 与 `states no premise, while the survivor states one` 因此以清洗后的形态到达模型；DSH 那侧同一份结果是整个对象过 `cleanJson()` 递归清洗，两家都洗、只是覆盖面不同（本包"每个工具结果都过清洗"这件事本身还开在 ROADMAP 里）。`DISCIPLINE` 第 4 条那句"mixedPremises 组里前提不同的行不是彼此的复述"从此由引擎全执行，措辞一字未改。**这一批对本包尤其对味**：本包宿主写的多是**不写前提约定的散文行**，"同一句话重述一遍并补个条件"是常见动作，旧行为等于用一次重述把通说的覆盖面收走。**第十一批（RR1 / RR2 / RR3）还是同一位复测者，这回两条 P0 方向相反、互为镜像**：写侧 RR1 是上一批那一形的另一半——G4 那道闸门问的是"这两笔是否**逐字**相同"，于是"同一句通说 + 一个**不同的值** + 一个新前提"读成覆盖，通说照样被一句话收走（四处退役站点接了三个，漏的是按相似度退役的那条 `brink` 臂）；读侧 RR2 更冷——库里那条**逐字就是被问的这句话**的行，被一条讲的是另一件事、且根本没声明前提的通说行从 support 席位上挤下去，于是它从 `support` / `newer_related[]` / `contradicting[]` / `superseded_matches[]` 四个出口一起消失（bge 实测 0.622 顶掉 0.862）；RR3 是 `stale_support` 有两条由头而 note 只有一条出口，把"归档版本站在后面"指给一个空数组——第三次抓到同一形状（G3 修假冲突、F2 修假 "assert the OPPOSITE"，这回旗标是真的）。**本包仍无代码改动**，`outcome` / `warning` / `note` 逐字段透传；对用户可观测的是三件事：带前提的换值写入回 `outcome: new` + `premise-narrowing:`（不再静默退役旧行）、上面那种库形状里 `support` 换成逐字复述那条并转 `out_of_scope`、归档造成的 staleness 不再让读者去查空的 `newer_related[]`。**仍未收**：`DISCIPLINE` 没有点名 `premise-narrowing:` 这条新警告，也没说"通说重述会多出一行"——模型第一次遇到并存可能顺手 merge，而 merge 现在会拒（拒得对，但多一轮）。这一处与 ROADMAP 里"描述只在一个出口可达"那一格同族，已并进去，不在本轮改适配器文案（改文案要配指令面用例，那是另一批）。**活宿主仍未跑**：opencode 里真实一轮 verify / remember 轮次。

## [0.3.0] — 2026-09-20（需要引擎 `hippo-memory-core@^0.3.0`）

### Added

- **`memory_remember` 新增 `scope` 参数**（`key=value; key=value`）：声明这条结论在什么条件下成立。响应回显 `scope`；前提与存量行对不上时新写**不覆盖旧行**，两条并存并带 `different-scope:` 警告。
- **`memory_verify` 新增 `scope` 参数与 `out_of_scope` 返回**：库里那条是在别的前提下说的 → 答 `OUT_OF_SCOPE`（`substantiated` / `contradicted` 双假），不再把旧前提下的结论盖到当前问题上。支持行带前提而提问没给 scope 时，note 里出现 `CONDITIONAL SCOPE`。
- **`memory_recall` 命中带 `scope`**（`hitView` 透出），同一主题多个前提各一行时可分辨。
- **注入的使用纪律更新**：写入一条要求"只在条件下成立就带 `scope`"；查证一条要求"`out_of_scope` 说明记忆里的答案属于别的前提，不得搬用"。

> 依赖引擎带 `scope` 的新版本，下限已提到 `hippo-memory-core@^0.3.0`（带 `scope` 与 fuzzy 归档修复）。配旧引擎不报错：`scope` 被忽略、`out_of_scope` 恒为 `false`。

### Fixed — 第九轮实测反馈：适配层两处透传缺口（与 DSH 同构）

- **`memory_recall` 补 `scope` 参数并透传引擎**：此前 recall 工具**根本没有 `scope` 入参**，传给 `store.recall` 的 cue 也不含它——前提硬过滤在工具面完全不生效。现在加 `scope` 入参、透传给 cue，返回补 `scopeExcluded`（`?? null` 规范空值），description 补一句"问题带前提就传 scope"。
- **`memory_remember` 回显 `verify_result` / `verified_at`**：原样复述并带新证据时，证据落到存储行但返回对象不透出，调用方看不到复述是否带上了证据。现补齐两字段。
- 均为适配层透传修复；`sourceMonitor` 的 fuzzy 归档误报订正在 `hippo-memory-core`（见根 CHANGELOG）。本包与 DSH 适配层为结构同构改动。

### Added — ② 重复合并：`memory_maintain merge` / `undemote`

- **新增 `merge` 动作**：`{ action: "merge", ids: [一个 duplicates 组的 id] }`，**默认预览**（`dry_run !== false`），`dry_run: false` 才落地。返回 `survivor` / `retired[]` / `carried[]` / `blocked[]` / `note`，全部文本过引擎 `sanitizeMemoryText`（引擎抛回的拒绝理由也清洗——理由里有记忆原文）。
- **补上 `undemote` 动作**：此前提示语承诺"折叠可回滚"，但 opencode 侧根本没有恢复入口，承诺是假的。现在 `{ action: "undemote", ids: [...] }` 直接透传引擎的 `{ restored[] }`。
- **`duplicates` 报告变宽并清洗**：每行带 `scope`，组级带 `mixedPremises`（组里至少有一对行前提互斥即为 true）。提示语据此写明"这类组里与幸存行前提相符的行照常折叠，冲突的行留在 `blocked[]`"。
- **`merge` 是折叠不是删除**：多余行仍在库里、默认召回不出现、`list` 仍列出（引擎 `StoredMemory.demoted` 原样透出）。DSH 版 `list` 这次补了 `demoted` 字段，本包因为直接返回引擎对象所以本来就有。

### Added — ③ digest 门槛没过时不再空白

零命中 digest 现在可能带第 1 行 `[low-confidence sim 0.31 < floor 0.32: the closest trace, not a memory — verify before asserting]`（引擎产出，适配层不额外渲染）；同时零命中不再回填 `[recent]` 近况。**`DISCIPLINE` 补一句解释这行是什么**（门槛以下的猜测、不是记忆、不得当作已存事实复述），否则模型会把它当成过了门槛的证据引用。

### Added — ④ `status` 看得见隔壁那个库

- **新增 `path_rule`**：说明本项目的库文件名怎么来的（按项目目录 slug 分库；`sharedStore: true` 时所有项目写同一个 `shared.db`）。
- **`diagnostics` 整体透出**：`sibling_stores`（缓存目录里每个 `.db` 的 `rows` / `demoted` / `lastWrite` / `current`）、`scope_rule`、`coverage` 直接可在 `status` 里读到。
- **`health` 先判"本库空、隔壁满"**：这种情形说的是"这条记忆写在另一个库里"并提示 `sharedStore`，而不是原先那句嵌入器不匹配——opencode 按项目分库，过去这两种故障输出同形。

### Changed — 注入的使用纪律

`DISCIPLINE` 第 4 条（MAINTAIN）现在点名 `status` / `duplicates` / `merge` / `undemote`，并写明"`delete` 会连版本历史一起删，清重复该用 `merge`"。纪律里不提的工具模型不会想到去用，所以这一段是 `merge` 在 opencode 里真正可达的前提。新增测试断言这段文案包含 `merge` 与 `low-confidence`。

  **optional peer 不会被安装** → 插件里 `import('@opencode-ai/plugin')` 失败 → `tool()` 拿不到 →
  4 个 `memory_*` 工具的参数 schema 退化成空对象，模型收不到任何字段定义（工具看起来"在"但不可用）。
- SDK 缺失时不再静默降级：通过宿主 logger 打一条 `WARN @opencode-ai/plugin is not resolvable…`。

### Verified

- 装上真实 `@opencode-ai/plugin@1.18.31` 后：`memory_remember.args.*` 带真实 `~standard`（zod）schema，
  `execute()` 写入返回 `outcome:"new"`，6 个钩子齐全；适配层 12 项测试在"有 SDK / 无 SDK"两条路径下都通过。

## [0.2.1] — 2026-09-18

### Changed

- 版本号与 `hippo-memory-core` / `dsh-hippo-memory` 对齐到同一条发布线（0.2.1），首次发布到 npm。

### Fixed（文档）

- 安装说明补充：opencode 对 `plugin` 数组里的**纯包名**会去 npm registry 现装到 `~/.cache/opencode/packages/<spec>/node_modules/<name>`，
  **不会**读 `~/.config/opencode/node_modules`。所以在配置目录里手工 `npm install` 一个未发布的包，插件会被静默丢弃：
  安装失败只发一条 Bus error 事件（TUI 一次性提示），日志文件里没有任何记录（服务端 report 的 `missing` 回调是空函数）。
  包发布到 npm 之后，`opencode plugin -g opencode-hippo-memory` 才是可用路径。
- 数据位置说明：store 根目录是**按环境**决定的 —— `XDG_CACHE_HOME` 优先，Windows 走 `%LOCALAPPDATA%\opencode\hippo-memory`，
  其余平台走 `~/.cache/opencode/hippo-memory`。同一项目在 Windows 与其它平台落在不同文件，跨平台迁移需自行拷贝 `.db`。
