# Changelog

## [0.3.2] — 2026-09-25（批次日期）／ **2026-10-06 发布 npm**（同日 **0.3.3** 仅重发本包文档，代码成员与 0.3.2 逐字节相同）— `memory_verify` 的返回值补上两种"不是 yes"；本包另有两条自家缺陷：每轮自动注入用的召回 cue **在真实宿主里恒为空**（A1），以及**没声明的参数被静默丢掉而调用方收到 `ok`**（F5）；引擎第七批的 `anchored` / `anchors` 一并透传（需要引擎 `hippo-memory-core@^0.3.2`）

本版把引擎侧 `verify` 的契约订正透传给宿主与模型：**yes 现在需要锚**，`OUT_OF_SCOPE` 现在会点名否决它的那条前提。缺陷本体、根因与修都在引擎，见根 [CHANGELOG.md](../../CHANGELOG.md) 的 `[0.3.2]`。**除透传之外本包还改了两处自己的东西**：A1（`latestUserCue` / `isInjectedNode`）——自动召回从上线起就没按当前任务检索过；F5（`defineClosedTool`）——没声明的参数名过去被直接扔掉、调用方拿到成功，现在一律拒绝并回显声明表。

### Changed — `memory_verify` 工具面

- **返回新增 `weak_match` / `scope_conflicts`**（`weak_match` 缺字段时规范为 `false`，`scope_conflicts` 规范为 `[]`）：前者=有痕迹越过召回线、但没有任何东西把它锚到这句话上（只是同话题，不是证据）；后者=与调用方 `scope` 前提冲突、且匹配度不低于所选支持的那些痕迹——它们的存在使裁决成为 `OUT_OF_SCOPE`，即使其中没有一条抢到 support 位。
- **description 改为点名五种结局**：SUBSTANTIATED / CONTRADICTED / OUT_OF_SCOPE / WEAK_MATCH / UNSUBSTANTIATED，并写明"只有 `substantiated: true` 可作为记住的事实复述；`weak_match: true` 不得靠读它的 support 升成 yes"。
- **注入的使用手册（`GUIDANCE`）第 3 条同步**：补上"weak_match:true 说的就是这个"，避免模型把 note 里的 `WEAK_MATCH` 当成"查过了、只是没查到"。

### Fixed — A1：自动召回用的 cue 恒为空串——digest 从上线起只按"最近写入"取，从没按当前任务取过

- **症状**（对宿主真实日志取证：`.hippo/probe-session-api.mjs` 把整个会话注册表重放进宿主自己的 `foldSurface()`——366 个日志文件、1,046,504 条事件、9,580 个 `user/message` 节点、331 次折叠、其中 284 个会话的 surface 非空）：**284 个会话里 `latestUserCue()` 返回 284 次空串**。理由是它遍历的 `session.surface.nodes` 类型是 `readonly SessionSeq[]`（`dsh-session/lib/types/surface.d.ts:120`，`surface.js:439` 往里 push 的是 `plan.seq`）——**元素是数字，不是消息对象**，`typeof node === 'object'` 一条都不成立，候选数组永远为空，函数落到"session 标题 / goal"兜底后返回 `''`。
- **为什么一直没炸**：空 cue 不是错误。`composeContext('')` 在引擎里有专门的空 cue 出口（告警 `empty cue: showing recently updated memories`），照样渲染出行。已发布 digest 的落盘统计（`.hippo/probe-digest-text.mjs`）：3,143 个 `hippo-memory:digest` section 里 **1,345 个带记忆行**、196 个是"记忆库为空"那句、1,562 个是"异步还没算好"那句。管道每轮都在动、每轮都有内容，只是**每轮给的都是最近写入的那几条**——cue 与当前任务的相关性从没参与过检索。合成库对照（`.hippo/probe-empty-cue.mjs`）：`cue=''` → items=5 且带 `empty cue` 告警，`cue='release gate'` → items=3 且无该告警。
- **修法**：`latestUserCue` 先取宿主的消息投影 `deriveMessages()`（`dsh-session/lib/index.js:1514`，返回这些 seq 所代表的 Message），取不到才回落到 `surface.nodes`（老宿主、或未来形状再变时至少不会静默倒退成"遍历数字"）。`isInjectedNode` 一并从"猜字段名"改成按**实测归属**读：先看 `source.kind`，`plugin` 只作旧形状的回落。
- **`role:'user'` 不等于人**（这条决定了修完之后不能只按角色取）：宿主把一大批别的东西也投影成 user 角色——**14,469 个 tool 结果 vs 3,387 个 `source.kind === 'user'`**，另有 skill-catalog 601、time-context 411、agent-instructions 200、model-selection 60……人只等于 `source.kind === 'user'` 那一支（`dsh-llm/lib/types/message.d.ts:110 MessageSourceMap`）。
- **上一轮写进 ROADMAP 的那条"危险"被取证否证**：原话是 `isInjectedNode`（本包 0.3.1 那一份把它写在 170 行；今天的它在 `packages/dsh-hippo-memory/lib/index.js:152`，那个 170 只是历史行号，故意不写成引用形式——写成引用形式它就会进上面那两个计数器，而计数器不会告诉你它指的是哪一份文件）"可能在读一个本宿主从不设置的字段"。**不是**——带我们 digest 标记的节点 3,152 个，其中 2,345 个归属 `{kind:'plugin', plugin:'@deepseek-ai/dsh-system-prompt', form:'snapshot', sections:[{name:'hippo-memory:digest'}]}`，798 个走 `kind:'runtime-context'`。**而这条否证差点被我自己写成相反的结论发布**：第一版探针读 `ev.source ?? ev.message?.source`，打印 `source key sets: [] ×897`，那是**路径读错**而非宿主事实（`dsh-session/lib/types/surface.js:91` 让 `user/message` 事件直接投影 `event.data`，没有 `.message` 这一层）。另外 `stripDigest` 那道内容清洗仍是必要的 belt，不能被白名单替掉：3,152 个带标记节点里有 **5 个挂在 `kind:'user'` 上**（累加器把上一轮的 digest 引进了人类轮次），白名单会放它们过。

### Fixed — F5（黑盒报告 #6，本包自家缺陷）：没声明的参数被丢掉，而调用方收到 `ok`

- **症状**：`memory_remember({ content, detail2 })` 这一形**返回成功**——`.hippo/blackbox-repro.txt` §F 在临时库里量到单行 32 个列里没有任何一列携带 `detail2`，本包自己的 list 视图也不吐这个键，而引擎那边既不报错也不落盘。写的人以为写进去了。（缺陷方向与 A1 相反但同源：**沉默的丢弃**——A1 是"每轮都在注入、注入的却不是你问的"，这一条是"每次都返回成功、成功的却不是你以为的那件事"。）
- **根因**：本包按声明表**取已知键**（`lib/index.js:301` 的 `defineClosedTool`，声明集来自同一处的 `Object.keys(params?.properties ?? params)`），从不检查**多余的**键。声明用的是扁平 `name -> schema` 形式，所以这道守卫先把 `parameters.properties` 嵌套形式也认下来，免得将来换成 JSON Schema 时它**静默变成空操作**——那种失效和没有守卫长得一模一样。
- **修法**：未声明的参数名一律**拒**，回显 `unknown argument(s) … — not declared, so nothing was read or written. Declared: …`，让一次拼写错误在第一次调用后就终止。`memory_remember` / `memory_recall` / `memory_verify` / `memory_maintain` / `memory_status` **每个工具各自过这道边界**，不是只给写入那一个装（用例 `F5: every memory tool guards its own boundary`）。
- **未收（写在这里而不是藏在根目录）**：这层保护只在**适配层**边界上——直接用 `HippoMemory.remember({...})` 的调用方仍不受约束；参数的**值类型**照旧不校验，这一轮只管名字。两条都在 [ROADMAP](../../ROADMAP.md) 在册。

## [0.3.1] — 2026-09-25 — 适配 DSH 0.1.7 配置接口（破坏性宿主版本）

0.1.7 删掉了 `settings.register()` 与客户端的 `settingsScope`，本插件在旧接口上会**整机启动失败**（`TypeError: settings.register is not a function`），四个 `memory_*` 工具全部消失。本版迁到宿主新配置面，并把"配置层不得拖垮挂载"钉成测试。

### Changed — 宿主半侧改用 volatile Config

- 不再注册 `hippo-memory` settings 命名空间：改为导出 `Config = z.object({...})`，五个字段全部 `.volatile()`。命名空间由 profile 条目 id（`hippo-memory`）推导，插件自身不注册任何东西。
- 生效配置从 Loader 交来的引用 `config.<field>.get()` 现读；**引用缺失或宿主给的是裸值时回落到 schema 自己的 `meta.default`**，不再抛错。默认值只写在 schema 一处，插件与配置面不可能各说一套。

- 浏览器半侧改用 `ctx.configForms.get('hippo-memory')` + `ctx.configForms.whileServed(...)`，配置页槽位从 `settings.plugin.item` 换成插件页的 `plugins.row.config`（key `dsh-hippo-memory#hippo-memory`）。

- `engines.dsh` 从 `>=0.1.1-rc.1` 提到 `>=0.1.7-0`（`.volatile()` 在更早的 schemastery 上不存在；`-0` 让 0.1.7 的 prerelease 也算满足）。删除两个宿主已不再提供的 `require`（`@deepseek-ai/cordis`、`@deepseek-ai/dsh-client-store`）。

## [0.3.0] — 2026-09-20（需要引擎 `hippo-memory-core@^0.3.0`）

### Added — 前提作用域透传到工具面

- **`memory_remember` 新增 `scope` 参数**：`key=value; key=value` 形式声明这条结论在什么条件下成立（`population=…` / `comparator=…` / `release=…`）。响应回显 `scope`（未写为 `null`）；前提与更近的存量行对不上时**不会覆盖它**，各存一条并带 `different-scope:` 警告。
- **`memory_verify` 新增 `scope` 参数 + `out_of_scope` 返回**：带着前提去问，库里属于别的前提的那条会答 `OUT_OF_SCOPE`（`substantiated` 与 `contradicted` 都为 `false`）而不是被盖章支持；支持行带前提而提问没给时，note 出现 `CONDITIONAL SCOPE` 并说明该前提未被核对。工具描述里补上了这第四种结局。
- **`memory_recall` 命中带 `scope`**：同一主题在不同前提下各有一行时，靠这个字段分辨 agent 看到的是哪一条。
- **`memory_maintain list` / `history` 透出 `scope`**（与其它文本同样过注入清洗），审查"这条是在什么口径下测的"不用回到对话里翻。
- **注入的记忆纪律更新**：第 1 条要求"只在条件下成立的结论要带 `scope`"，第 3 条要求"带 scope 去 verify，`out_of_scope` 时不得把那个答案搬到当前前提下"。

> `scope` / `out_of_scope` 依赖引擎带该字段的新版本。配旧引擎不会报错：`scope` 被忽略、`out_of_scope` 恒为 `false`，其余行为与本版之前一致。依赖下限已提到 `hippo-memory-core@^0.3.0`（即带 `scope` 与 fuzzy 归档修复的引擎）。

### Fixed — 第九轮实测反馈：适配层两处透传缺口

- **`memory_recall` 补 `scope` 参数并透传引擎**：此前工具 schema 没有 `scope` 入参，传给 `store.recall` 的 cue 也不含它——引擎从没收到，前提硬过滤在工具面**完全不生效**（`scopeExcluded` 恒为 `undefined`）。现在加 `scope` 入参、透传给 cue，返回补 `scopeExcluded`（前提冲突行被排除时计数，`warnings` 附 `scope:` 说明）。实测：带 `scope=env=prod` 查询不再把 `env=test` 的行当答案（`scopeExcluded=2`）。
- **`memory_remember` 回显 `verify_result` / `verified_at`**：原样复述并带新证据（`verify_result:"pass"`）时，证据已正确落到存储行，但返回对象没透出这两个字段，调用方看不到复述是否带上了证据。现补齐（`cleanJson` 把 `undefined` 规范为 `null`，故键恒在、无证据时为 `null`）。
- 均为适配层透传修复，`sourceMonitor` 的 fuzzy 归档误报订正在 `hippo-memory-core`（见根 CHANGELOG）。

### Added — ② 重复可以合并：`memory_maintain merge`

- **`memory_maintain` 从 12 个动作变 13 个**：新增 `merge`。`{ action: "merge", ids: [一个 duplicates 组的 id] }` 默认**预览**（`dry_run` 未给即为 true，返回谁留下、谁被折、`carried[]` 结转了什么、`blocked[]` 因何不动），`dry_run: false` 才落地。参数表补 `into`（点名要留的 id，必须是 `ids` 之一）与 `dry_run` 说明。
- **为什么不该再用 `delete` 清重复**：`delete` 连版本历史一起消失，`merge` 只把多余行折叠（`demoted`）——行还在库里、默认召回不再出现、`undemote` 随时恢复。`duplicates` 的提示语现在把这条路写清楚（"review, then merge a group you confirmed… or remove ids with action delete (history is removed with the row)"）。
- **`duplicates` 报告变宽**：每行带 `scope`，组级带 `mixedPremises`（组里至少有一对行前提互斥即为 true）。提示语据此写明：这类组**不是整组作废**，与幸存行前提相符的行照常折叠，冲突的行留在 `blocked[]`。
- **`list` 新增 `demoted` 字段**：合并 / 压缩过的行本来就一直出现在清单里，但此前没有任何标记，agent 分不清哪条是被折的、也就拿不到 `undemote` 要用的 id。现在每行带 `demoted: true/false`。

### Added — ③ 门槛没过时 digest 不再空白（本适配层无代码改动）

召回全部低于门槛时，digest 第 1 行是引擎给的最接近痕迹并带 `[low-confidence sim … < floor …: the closest trace, not a memory — verify before asserting]`；零命中时不再回填 `[recent]` 近况。适配层的渲染不变（digest 整体来自引擎），但**使用纪律补了一句解释**：见下面的 GUIDANCE 变更。

### Added — ④ `status` 看得见隔壁那个库

- **`status` 新增 `path_rule`**：一句"本宿主的库文件名是怎么来的"——开 `sharedStore` 时说明所有 agent 共用一个文件，否则说明"每个 agent id 一个文件，别的 agent 记的东西在这里看不到（要合并请开 sharedStore）"。
- **`diagnostics` 整体透出**，因此引擎新增的 `sibling_stores`（同目录每个 `.db` 的 `rows` / `demoted` / `lastWrite` / `current`）、`scope_rule`（"记忆不跨库文件流动"这条契约）与 `coverage`（本进程 digest 的 `turns` / `misses` / `guesses`）在 `status` 里直接可读，不需要改渲染层。
- **`health` 判定顺序改为"先看库分裂"**：本库 0 行而隔壁有货 → 直接说"这条记忆写在另一个库里"（点名 agent 维度），其次才是嵌入器不匹配。DSH 按 agent id 分库，所以"没记住"与"记在另一个文件"在工具输出里过去完全同形。

### Changed — 注入的使用纪律（模型能不能看见这些能力）

- `GUIDANCE` 第 4 条（MAINTAIN）现在**点名** `status` / `duplicates` / `merge` / `undemote`，并写明 `mixedPremises` 组的读法和"`delete` 会连版本历史一起删"。一条工具如果纪律里不提，模型基本不会想到去用——这是本批唯一让 `merge` 真正可达的改动。
- `GUIDANCE` 第 5 条补一句：digest 里 `[low-confidence …]` 那行是**门槛以下的猜测**，不是记忆，断言前须复查、不得当成已存事实复述。
- 新增测试锁住这段文案（纪律里必须出现 `duplicates` / `merge` / `low-confidence`），避免以后改提示词时把可达性悄悄改掉。
